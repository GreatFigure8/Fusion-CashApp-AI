# Plan: s14-receipt-watcher-rematch

Issue #14. Wave 3. Python only (`cashapp/` = `api/src/cashapp/`); no web, no UI.

## Standards followed

- CLAUDE.md non-negotiable 5: this is **poller 2 of exactly 2**. It's a long-running async loop inside a worker. Its interval is re-read from runtime config every cycle, and its only output is outbox events (plus aging escalations, which run on the same cycle; see the story assumption). The consumer is event-driven and is not a poller.
- CLAUDE.md *The assembly line*:
  - The watcher filters on **creation time**, not receipt date.
  - The high-water mark lives in the DB, so a restart neither misses nor replays receipts.
  - There's no fixed hold: items wait in `AWAITING_RECEIPT` and are re-matched on arrival, with aging and escalation.
  - Transactional outbox: a state change, its history row and its event are written in one transaction. Consumers are idempotent and check state before they act. Offsets are committed only after the DB commit.
- Layering (s02 test): no `sqlalchemy` import outside `cashapp/data/`. Repositories never commit. Services own the transactions and take plain arguments (no `Request`). The poller and consumer call services, and services call repositories.
- Reference doc §6 timing lessons: about 67% of failures fix themselves given time, and receipts are often created a day after their receipt date. So the wake check accepts the payment date within the window of **either** `receipt_date` or `creation_date`.
- `python-web-app:building-python-web-apps`:
  - integrations stay behind interfaces (`FusionClient` comes from `container.resolve`)
  - `Clock` and config are injected
  - every schema change is one hand-written Alembic revision
  - unit tests run on aiosqlite, with `-m atp` tests for SKIP LOCKED
- `python-web-app:wiring-application-config`: config is read only through s28 accessors. No new config keys are added; the watcher's constants are constructor kwargs with pinned defaults.
- Money is `Decimal` (`to_money`, `MoneyStr`), serialised as strings in the event. All datetimes are tz-aware UTC (`UtcDateTime`).
- DB naming (s02): lowercase SQLAlchemy names, no reserved words, identifiers of at most 30 characters, no CHECK constraints on enum columns.
- Coder gates: `uv run ruff check . && uv run ruff format --check .` and `uv run pyright` (strict on `src/`). Tests are written and run only in step 5.

## Design

### Event (`domain/receipt_arrived.py`)

- `ReceiptArrived` is frozen with `extra="forbid"`, and has `schema_version: Literal[1] = 1`.
- Money fields are `MoneyStr`, so they serialise as strings.
- `from_fusion(r: FusionReceipt, *, event_id=None)` maps s05's `FusionReceipt`. The import is under `TYPE_CHECKING` only, so the domain module stays free of integrations.
- Topic: `default_namer().named(RECEIPT_ARRIVED_TOPIC)`, which gives `cashapp.<env>.receipt-arrived` (s25 already provisions a `receipt-arrived` stream). The message key is `str(receipt_id)`.
- s30's `InFlightTrackingBus` fails to parse this payload as a `StageEvent` (`extra="forbid"`), so it passes through untracked. That's intended: it holds no stage slot.

### Watermark cursor (`pollers/receipt_watcher/cursor.py`, pure)

```
OVERLAP = timedelta(minutes=5)          # AC2
INITIAL_LOOKBACK = timedelta(hours=24)  # first run only, no row yet

select_new(receipts, mark, seen, overlap=OVERLAP) -> list[FusionReceipt]
    drop r if r.creation_date < mark - overlap         (defensive; the query is >=)
    drop r if str(r.receipt_id) in seen                (already emitted)
    dedupe by receipt_id (first wins); keep Fusion order (creation asc, id asc)

advance_mark(mark, seen, emitted, overlap=OVERLAP) -> tuple[datetime, dict[str, str]]
    new_mark = max(mark, max(r.creation_date for r in emitted))   (unchanged when nothing emitted)
    seen'    = seen ∪ {id: creation ISO for emitted}
    prune seen' to entries with creation >= new_mark - overlap
```

A receipt that becomes visible late, with a creation time inside the overlap window, is still emitted, because the dedupe is by id and not by "older than mark". Ties at the mark across cycles are covered by the `seen` map.

### `ReceiptWatcher` (`pollers/receipt_watcher/watcher.py`)

```
run(stop):
  loop until stop:
    snap = await config.snapshot()
    interval = max(1, snap.receipt_watcher().poll_interval_seconds)   # re-read every cycle (AC2)
    try: stats = await run_cycle(snap)  → status running, last_activity_at, log stats
    except Exception as e: log type only; status degraded (detail = type name)
    await asyncio.wait_for(stop.wait(), interval)  (TimeoutError → next cycle)
  status stopped

run_cycle(snap) -> WatcherCycleStats:
  1. emitted = await _ingest_receipts()      (own try: a FusionError marks the cycle degraded, but aging still runs)
  2. aged    = await _age_out(snap)
```

`_ingest_receipts` loops over at most `max_batches_per_cycle` (default 20):

1. **Read** the cursor in a short UoW without a lock: `repo.by_pod(pod)`. If there's no row, `mark = clock.now() - INITIAL_LOOKBACK` and `seen = {}`.
2. **Fetch** outside any transaction: `receipts = await fusion.receipts_created_since(mark - OVERLAP, limit=limit)`.
3. **One transaction per batch** (AC2):
   1. `wm = await repo.lock_or_create(pod, initial_mark, now)`. This is `SELECT … FOR UPDATE` (it waits). If there's no row, it inserts one and flushes; a unique violation from a racing replica → roll back and end the cycle (the next cycle continues).
   2. `new = select_new(receipts, wm.high_water_mark, wm.seen_at_mark)`. The cursor is recomputed against the **locked** row, so two watcher replicas never emit the same receipt twice.
   3. For each receipt in `new`: `enqueue(uow, topic=…, key=str(receipt_id), payload=ReceiptArrived.from_fusion(r), priority=PRIORITY_LIVE, clock=clock)`.
   4. `wm.high_water_mark, wm.seen_at_mark = advance_mark(...)`, then `updated_at = now`.
   5. `await uow.commit()`.
4. **Continue or stop:**
   - `len(receipts) < limit` → done.
   - Full batch with progress → loop.
   - Full batch with **no** new receipts (more than `limit` receipts inside the overlap window, for example a lockbox import with one timestamp) → `limit = min(limit * 2, max_limit)` and refetch. At `max_limit`, log a warning, set degraded and stop the cycle.

Crash semantics:

- A crash between the fetch and the commit leaves the mark and the outbox unchanged, so the next cycle refetches and emits.
- A crash after the commit means the mark and seen already cover what was emitted, so nothing is replayed.

`_age_out` loops until a batch comes back short:

1. In one UoW: `items = await AwaitingReceiptRepository.aged_out(cutoff=now - timedelta(days=snap.aging().awaiting_receipt_max_days), now=now, limit=aging_batch)`. This is `FOR UPDATE SKIP LOCKED` and excludes live locks.
2. `await escalate_aged(uow, items, max_days=..., clock=clock)`.
3. Commit.

The loop is bounded to `max_batches_per_cycle` batches.

### Wake service (`services/awaiting_receipt.py`)

```
wake_for_receipt(uow, event, *, matching: MatchingConfig, clock) -> WakeResult
  window    = matching.date_window_days
  tolerance = matching.tolerance_for(event.currency)
  items = await uow.repo(AwaitingReceiptRepository).candidates_for(event, window, tolerance, now=clock.now())
  for item in items:                       # already locked, state re-checked
      from_stage = item.stage
      item.stage, item.state = MATCH_RECEIPT, PENDING
      item.attempts = 0; item.claim_expires_at = None
      item.last_error_code = None; item.last_error_detail = None
      # keep awaiting_since (aging spans re-parks) and fix_hints (s18's match_on_creation_date)
      await record_history(uow, item.id, HistoryEntry(STAGE_TRANSITION, from_stage=from_stage,
            to_stage=MATCH_RECEIPT, from_state=AWAITING_RECEIPT, to_state=PENDING,
            reasoning=f"woken by receipt {event.receipt_number}",
            payload={"receipt_id", "receipt_number", "event_id", "currency", "unapplied_amount", "customer_account_number"}), clock=clock)
      await emit(uow, StageEvent.new(item.id, Stage.MATCH_RECEIPT, clock=clock), priority=item.priority, clock=clock)
  return WakeResult(woken_ids=[...], receipt_id=event.receipt_id)   # caller commits
```

```
escalate_aged(uow, items, *, max_days, clock) -> list[int]
  for item: await escalate(uow, item, ErrorCode.AGED_OUT, aged_out_summary(item, max_days, clock.now()))
  # s18 escalate: STATE=ESCALATED, LAST_ERROR_CODE, ESCALATION_SUMMARY, history, NotifyEvent via outbox
aged_out_summary(item, max_days, now) -> str
  # deterministic template, no LLM, no PII:
  # "No matching Fusion receipt appeared within {max_days} days (awaiting since {awaiting_since:%Y-%m-%d})."
```

### `AwaitingReceiptRepository.candidates_for` (data layer)

**Phase 1, a coarse SQL select of ids with no lock:**

- `state = 'AWAITING_RECEIPT'`
- `(currency = :cur OR currency IS NULL)`
- `(payment_amount IS NULL OR payment_amount <= :unapplied + :tolerance)`. This is AC4's `|amt − unapplied| ≤ tol OR amt ≤ unapplied`, reduced to one comparison.
- `(payment_date IS NULL OR payment_date BETWEEN :lo AND :hi)`, where `lo = min(receipt_date, creation_date.date()) - window` and `hi = max(...) + window`
- `(lock_owner IS NULL OR lock_expires_at <= :now)`
- `ORDER BY awaiting_since, id`, capped at `limit` (default 500; a log line when the cap is hit)

**Phase 2, exact filters in Python:**

- **Date:** the payment date is within `window` of `receipt_date` **or** within `window` of `creation_date.date()`. The two windows can be disjoint, so this can't be one `BETWEEN`.
- **Customer:** keep the item when `item.customer_account_number == event.customer_account_number` or the receipt's customer is in the item's latest `CUSTOMER_RESOLUTION.RELATED_CUSTOMER_NUMBERS`.
  - The related numbers come from **one batched query** over s11's `CUSTOMER_RESOLUTION` ORM model for the phase-1 ids (latest row per item by `created_at, id`).
  - A JSON-contains predicate would differ between Oracle and SQLite, so the filter runs in Python.
- A receipt with no customer (`customer_account_number is None`) wakes nothing (see assumptions).

**Phase 3, lock:**

- `select_for_update_skip_locked(WHERE id IN (:ids) AND state='AWAITING_RECEIPT' AND (lock_owner IS NULL OR lock_expires_at <= :now))`.
- Rows another transaction holds are skipped: that transaction is either waking them already or changing their state.
- `is_locked_for_automation(item, now)` (s40) is re-checked on each locked row as a belt-and-braces check.

`aged_out(cutoff, now, limit)`:

- `state='AWAITING_RECEIPT' AND awaiting_since IS NOT NULL AND awaiting_since < :cutoff AND (no live lock)`
- `ORDER BY awaiting_since, id`, `FOR UPDATE SKIP LOCKED`, `limit`
- It uses `IX_WORK_ITEM_STATE_AWAITING`.

### `ReceiptArrivedConsumer` (`stations/receipt_arrived/consumer.py`)

It's a Runnable and not a `StageRunner`: the event carries a receipt, not a work item, so there's nothing to claim. It still follows s03's consumer contract.

- It subscribes to `[namer.named(RECEIPT_ARRIVED_TOPIC)]` with `group = settings.streaming.consumer_group`, unchanged. Deliveries are processed one at a time; about 3k receipts a day needs no concurrency.
- For each delivery:
  1. **Parse** with `ReceiptArrived.model_validate_json`. On `ValidationError`, `enqueue` `{error: "malformed", source_topic, partition, offset, raw: <utf-8, replace, ≤ 4000 chars>}` to `namer.named("receipt-arrived.dlq")` in its own UoW, commit, commit the offset and continue.
     - This goes through the outbox, not `bus.publish`, so s03's `test_only_outbox_publishes` stays green.
  2. `snap = await config.snapshot()`.
  3. In one UoW: `wake_for_receipt(uow, event, matching=snap.matching(), clock=clock)`, then `commit`.
  4. `await delivery.commit()` only after the DB commit. Log `receipt_id` and the woken count; never log payload contents beyond ids.
  - **Redelivery is a no-op:** the woken items are now `PENDING`, so phases 1 and 3 exclude them.
  - **Infrastructure error** (the DB is down): don't commit the offset. Status becomes `degraded`, then a bounded backoff (1, 2, 4 … 30 s, interruptible by `stop`) before retrying the **same** delivery. This mirrors s03's `StageConsumer`.
- On `stop`, it finishes the current delivery and leaves (`aclose` on the subscription).

## Risks

- **Lost wake-up race.** An item that parks (s18) **after** the consumer has handled a receipt that could match it is not woken by that receipt.
  - The window is small: s13 must query Fusion just before the receipt is created, and the park must commit after the consumer runs.
  - It's bounded by later receipts for the same customer, by aging, and by human requeue.
  - Closing it fully would need a periodic re-sweep (a third poller) or s18 re-checking recent receipts at park time. That's recorded for Jonathan's ruling and not built.
- **s18 "first time park" semantics.** If s18 escalates on the *second* `RECEIPT_NOT_YET_AVAILABLE` (after a wake that didn't match), every false wake escalates the item.
  - s14 resets `ATTEMPTS` to 0 on wake.
  - s18 must re-park on every recurrence and leave the bound to aging (`AGED_OUT`). Flagged to s18's planner and merger.
- **s29 queue age.** A woken item keeps `AWAITING_SINCE` (needed so aging spans re-parks). While it's `PENDING` at `MATCH_RECEIPT`, s29's `oldest_age_s` (which prefers `awaiting_since`) shows the total waiting time, not the time in stage. That's acceptable and documented for s19.
- **Candidate scan cost.** The customer filter runs in Python after a coarse SQL pre-filter (state, currency, amount, date and lock). At about 3k receipts a day and hundreds to low thousands of awaiting items, this is cheap. If volume grows, add an Oracle `JSON_EXISTS` predicate behind the repository (no interface change).
- **Bulk receipts with one `CreationDate`** (lockbox) above `max_limit` (10k) inside 5 minutes stall the cursor; the watcher degrades with a warning. s05's `receipts_created_since` has no offset paging. Recorded.
- **Unverified Fusion behaviour** (s05 marks it UNVERIFIED):
  - `CreationDate >=` filtering and ordering on `standardReceipts`
  - the timestamp precision of `CreationDate`

  Equal-precision ties are covered by `SEEN_AT_MARK`. The live check is in s05's `live` tests.
- **Same-wave dependencies:** s11's ORM class name and s18's `escalate` are coded against story-stated interfaces. If those plans pin different names, the merger reconciles the imports. No local stand-ins are made (non-negotiable 7).
- aiosqlite drops `FOR UPDATE [SKIP LOCKED]`. The concurrency claims are proven only by the `atp` tests.

## Assumptions and deviations

1. **`SEEN_AT_MARK` stores `{receipt_id: creation ISO}`** for every receipt emitted inside `[HIGH_WATER_MARK − OVERLAP, HIGH_WATER_MARK]`, not just ids that tie at the mark.
   - The story says it drops receipts "older than the mark". Doing that would defeat the 5-minute overlap: a receipt committed late with an earlier `CreationDate` would be dropped.
   - Deduping by id across the whole overlap window catches late-visible receipts and still satisfies the tie test.
   - The JSON shape is a map, so pruning needs no extra Fusion call.
2. The watcher's constants (overlap 5 min, initial lookback 24 h, batch limit 500 → max 10k, 20 batches per cycle, aging batch 100, candidate cap 500) are constructor kwargs with pinned defaults, not runtime-config keys. The story only names `poll_interval_seconds` as config.
3. `ReceiptArrived` lives in `cashapp/domain/receipt_arrived.py` (a new file outside the listed owned dirs), so the data-layer repository can type its argument without importing from pollers or pipeline.
4. The wake service lives in `cashapp/services/awaiting_receipt.py` (new) so business rules stay in the business layer. `candidates_for` takes a keyword-only `now` (needed for the lock rule) in addition to the story's `(receipt, window_days, tolerance)`.
5. The consumer is a plain Runnable, not a `StageRunner`, because there's no work item to claim per event. Malformed events go to `receipt-arrived.dlq` through the outbox (`enqueue`), not `bus.publish`.
6. Items with a null `PAYMENT_AMOUNT` or `PAYMENT_DATE` are treated as matching that criterion. This mirrors the story's null-currency rule, and s13 makes the real decision. A receipt with a null customer wakes nothing, because AC4 requires a customer match.
7. On a wake: `ATTEMPTS=0`, `LAST_ERROR_*` cleared, the claim cleared; `AWAITING_SINCE` and `FIX_HINTS` are kept. `FIX_HINTS.widen_window_days` isn't applied to the wake filter; s13 applies it when matching.
8. Aging escalation runs on the watcher's cycle (story assumption). The summary is a deterministic template, with no LLM call on this path.
9. The first run (no watermark row) backfills 24 hours of receipts. The extra events are harmless, because a wake is idempotent.
